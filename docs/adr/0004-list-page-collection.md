# ADR-0004: 목록 페이지에서 직접 수집한다 — `parse_page()` 로 프로토콜 일반화

- **상태**: **Accepted** — 2026-08-20 결정
- **관련**: 블루프린트 §3.1(`SourceAdapter`), §3.2 조사 체크리스트, §3.3 파이프라인 / T-007, T-014, T-017
- **근거 데이터**: 아래 §2 (모두 실측)

---

## 1. 문제

김밥레코즈의 바이닐 카탈로그는 **약 9,072건**(`cate_no=25`, 756페이지 × 12건)이다.
상세 페이지를 1건씩 가져오면 §3.4 의 0.5 req/s 상한에서 **약 5시간**이 걸린다.
30분 주기 갱신이 불가능하다.

## 2. 실측

### (a) 목록 페이지가 우리가 저장하는 모든 필드를 담고 있다

같은 상품(`product_no=32562`)을 목록과 상세에서 각각 파싱해 대조했다.

| 필드 | 목록에서의 위치 | 상세와 일치 |
|---|---|---|
| `source_item_id` | `li[id^="anchorBoxId_"]` 의 id 접미사 | ✅ |
| `title_raw` | `.description .name a span` | ✅ |
| `price_krw` | `.spec li span` | ✅ |
| `stock_status` | `img.icon_img[alt="품절"]` 유무 | ✅ |
| `thumbnail_url` | `.thumbnail img[src]` | ✅ |
| `label_raw` / `release_date_raw` | 없음 — **상세에도 없다** | ✅ |

상세가 추가로 주는 값은 `stock_number` 정확값과 `_iPrdtPriceOrg`(공급가)뿐인데,
**둘 다 `RawItem` 에 저장하지 않는다.**

### (b) 조건부 요청은 김밥에서 동작하지 않는다

```
ETag            : 없음
Last-Modified   : 요청 시각이 그대로 찍힘 (콘텐츠 변경 시각이 아님)
If-Modified-Since 재요청 → 200 OK, 본문 87,521 bytes 전송
```

304 를 주지 않으므로 조건부 요청으로는 트래픽이 줄지 않는다.

### (c) 상세 페이지는 `content_hash` 가 불안정하고, 목록은 안정적이다

같은 URL 을 2회 받아 비교했다.

| | 결과 |
|---|---|
| 목록 페이지 | **바이트 단위 동일** — 해시 안정 |
| 상세 페이지 | 해시 불일치. `var qrcode_class = 'EC_Qrcode6a86b81d98bb1'` 가 요청마다 난수 |

상세 기반을 유지하면 §3.3 의 `content_hash` 스킵이 **영원히 동작하지 않아** 매번 전량 재파싱하게 된다.
CLAUDE.md §6 이 "크롤을 예의 있게 유지하는 장치"라고 한 기능이 무력화된다.

## 3. 결정

**목록 페이지에서 직접 `RawItem` 을 만든다.** 이를 위해 §3.1 프로토콜을 일반화한다.

```python
# 변경 전
async def parse_item(self, url: str, html: str) -> RawItem | None: ...

# 변경 후
async def parse_page(self, url: str, html: str) -> list[RawItem]: ...
```

- `discover()` 는 이제 **"수집 대상 페이지 URL"** 을 반환한다 (목록이든 상세든)
- `parse_page()` 는 한 페이지에서 나오는 `RawItem` 을 **모두** 반환한다.
  목록이면 여러 건, 상세면 1건, 파싱 실패면 빈 목록
- §3.3 파이프라인의 fetch → 해시 → 스냅샷 흐름은 **그대로**다. 한 번에 다루는 건수만 달라진다

### 이 형태가 세 소스를 모두 담는다

| 소스 | `discover()` 가 내보내는 것 | `parse_page()` 반환 |
|---|---|---|
| gimbab | 목록 페이지 URL | 12건 |
| secondtrack | 목록 페이지 URL (동일 구조로 전환 가능, T-014) | N건 |
| poclanos | **상세** 페이지 URL (목록이 없어 ID 열거) | 1건 |

포크라노스처럼 목록이 없는 소스도 같은 인터페이스로 처리된다.

## 4. 효과

| | 요청 수 | 소요 시간 |
|---|---|---|
| 상세 전량 (변경 전) | 9,072 | 약 5시간 |
| **목록만 (변경 후)** | **756** | **약 25분** |

부수 효과로 `content_hash` 스킵이 실제로 동작하게 된다 (§2-c).

## 5. 감수하는 것

**구조화 데이터를 잃는다.** 상세 페이지에는 JSON-LD `Product` 가 있지만 목록에는 없다.
CSS 셀렉터에만 의존하게 되어 사이트 개편에 더 취약하다.
이는 블루프린트 §3.2 조사 체크리스트 6번("구조화 데이터가 있으면 셀렉터보다 우선")과 어긋난다.

12배의 비용 차이가 이를 압도한다고 판단했으나, 완화책을 둔다.

> **완화책 (T-018 파서 카나리에 포함)**: 하루 1회 **상세 페이지 1건**을 받아
> JSON-LD 파싱 결과와 목록 파싱 결과를 대조한다. 값이 어긋나면 셀렉터 파손으로 보고 알린다.
> 요청 1회짜리 보험이다.

이를 위해 어댑터는 상세 파싱 능력을 **버리지 않고** 내부 메서드로 남긴다.

## 6. 조사 체크리스트 보강

포크라노스 초회 조사에서 목록만 보고 "CSR 이라 수집 불가"로 잘못 결론낸 적이 있다(ADR-0002 §1).
이번에는 반대로 상세만 보고 목록의 가치를 놓칠 뻔했다. 블루프린트 §3.2 체크리스트에 다음을 추가한다.

> 4-1. **목록 페이지와 상세 페이지를 각각** 확인한다. JS 렌더링 필요 여부와
>      수집 가능한 필드는 **페이지 종류마다 다르다.**
> 5-1. 목록 페이지만으로 `RawItem` 의 필드를 모두 채울 수 있는지 확인한다.
>      가능하면 **목록 기반 수집을 우선**한다 (요청 수가 페이지당 건수만큼 줄어든다).
