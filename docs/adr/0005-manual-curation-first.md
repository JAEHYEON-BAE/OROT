# ADR-0005: 제품 방향 재정의 — 수동 등록 우선, 자동 수집 보류

- **상태**: **Accepted** — 2026-08-20 결정
- **관련**: 블루프린트 §1(문제 정의), §2(아키텍처), §4(데이터 모델), §5(API), §10(백로그)
- **대체 관계**: ADR-0001(예약 감지)의 보류 사유를 갱신한다. ADR-0002~0004 는 유효하나 **적용 시점이 뒤로 밀린다**

---

## 1. 무엇이 바뀌었나

프로젝트 소유자가 제품 정의를 명확히 했다.

> 전체 바이닐 판매 정보를 저장하는 디스콕스 같은 DB가 아니다.
> **신규 발매 일정과 예약판매 기간을 놓치지 않도록 돕는 앱**이다.
> 초기에는 **운영자가 일정을 직접 등록**하고, 자동 수집은 나중에 한다.

명시적으로 **핵심이 아니라고 확인된 것**:

- 판매처별 가격 비교
- 아티스트 디스코그래피
- 카탈로그 전수 수집

## 2. 왜 이 전환이 타당한가

### (a) 기존 성공 지표가 이미 이 방향을 가리키고 있었다

블루프린트 §1.3 의 지표는 **전부 지연·누락에 관한 것**이며,
"수집 상품 수"나 "카탈로그 커버리지" 항목이 **없다.**
9,072건을 전수 수집해도 성공 지표는 하나도 개선되지 않는다.

### (b) 수동 등록은 두 가지 위험을 분리한다

| 위험 | 자동 수집으로 검증할 때 | 수동 등록으로 검증할 때 |
|---|---|---|
| "이걸 원하는 사용자가 있나" | 크롤러가 안정화된 뒤에야 확인 가능 | **즉시 확인 가능** |
| "안정적으로 크롤할 수 있나" | 제품 검증과 뒤섞임 | 나중에 독립적으로 해결 |

제품-시장 적합성 검증을 크롤러 신뢰성에 인질로 잡히지 않게 한다.

### (c) 데이터 품질이 오히려 올라간다

조사 결과 **발매일을 제공하는 소스가 하나도 없다** (§3 참조).
자동 수집으로는 캘린더를 채울 수 없지만, 운영자는 정확한 날짜를 입력할 수 있다.

### (d) 예약 마감 시각은 어느 소스도 노출하지 않는다

"예약 기간"을 보여주려면 마감 시각이 필요한데, 세 소스 모두 제공하지 않는다.
**수동 등록만이 이 필드를 채울 수 있다.**

## 3. 자동 수집이 채울 수 없었던 것 — 실측 근거

캘린더 앱의 핵심 데이터인 날짜를 어느 소스도 구조적으로 제공하지 않는다.

| 소스 | 발매일 | 예약 시작 | 예약 마감 |
|---|---|---|---|
| 김밥레코즈 | **구조적 필드 없음** | 관측으로 추정만 가능 | **없음** |
| 세컨드트랙 | 정보 테이블 자체가 없음 | 관측으로 추정만 가능 | **없음** |
| 포크라노스 | 60KB 상세설명 안에 묻힘 (§3.4 저장 금지 대상) | 관측으로 추정만 가능 | **없음** |

자동 수집으로 얻을 수 있는 것은 상품명·가격·재고뿐이다.
**"일정"이라는 제품의 중심 데이터는 사람이 넣어야 한다.**

## 4. 결정

### 4.1 수동 등록을 1차 경로로 만든다

운영자가 발매 일정을 등록하고, 사용자는 공개 피드·캘린더·알림으로 받는다.

```
운영자 ──(관리 API, ADMIN_API_KEY)──► releases + release_links
                                            │
                                            ▼
                              공개 API (/v1/releases, /v1/feed)
                                            │
                          ┌─────────────────┼─────────────────┐
                          ▼                 ▼                 ▼
                     웹 피드/캘린더     RSS 구독        iCalendar 구독
```

### 4.2 알림은 시각 기반으로 만든다 (diff 기반이 아니다)

자동 수집 모드의 알림은 "직전 상태와 비교"(§4.5)였다.
수동 모드에서는 운영자가 `preorder_opens_at` 을 입력하므로,
**스케줄러가 그 시각을 보고 발송**한다. diff 엔진이 필요 없다.

| 시점 | 알림 |
|---|---|
| 일정 최초 공개 시 (초안 등록은 제외) | `SCHEDULE_ADDED` |
| `preorder_opens_at` 24시간 전 | `PREORDER_OPENS_SOON` |
| `preorder_opens_at` | `PREORDER_OPEN` (최우선) |
| `release_date` | `RELEASED` |

### 4.3 계정 없이 핵심 가치를 배송한다

푸시 알림(기존 M6)과 계정(기존 M4)을 기다리지 않는다.
**RSS 와 iCalendar 는 인증이 필요 없다.** 사용자가 자기 캘린더 앱에서 예약 일정을 구독하면
푸시 인프라도 로그인도 없이 핵심 약속이 배송된다.

### 4.4 이미 만든 자동 수집 코드는 **버리지 않고 잠시 재운다**

`fetcher.py`, `adapters/gimbab.py`, `registry.py`, 시드, 스키마는 전부 테스트를 통과한 상태로 남는다.
제품 루프에 배선되지 않을 뿐이며, M3(자동 수집 재개)에서 그대로 쓴다.
ADR-0002~0004 의 결정(목록 기반 수집, 포크라노스 상세 파싱, robots 파서)도 그때 유효하다.

## 5. 스키마 변경

`listings` 는 **크롤 산출물 전용**으로 남긴다 (`source_item_id`, `content_hash` 가 필수인 구조).
수동 등록 데이터는 `releases` 와 신규 `release_links` 에 들어간다.
나중에 자동 수집이 붙으면 크롤된 `listings` 가 같은 `releases` 에 연결된다.

### 5.1 `releases` 에 추가

```sql
ALTER TABLE releases
  ADD COLUMN preorder_opens_at  TIMESTAMPTZ,          -- 예약 시작 (알림 트리거)
  ADD COLUMN preorder_closes_at TIMESTAMPTZ,          -- 예약 마감 (수동만 채울 수 있음)
  ADD COLUMN curation           TEXT NOT NULL DEFAULT 'MANUAL'
             CHECK (curation IN ('MANUAL','CRAWLED')),
  ADD COLUMN is_published       BOOLEAN NOT NULL DEFAULT FALSE,  -- 초안/공개
  ADD COLUMN notes              TEXT;                 -- 운영자 메모 (비공개)
```

기존 `release_date`(DATE), `is_limited`, `format`, `variant`, `label`, `cover_url` 은 그대로 쓴다.

### 5.2 신규 `release_links` — 어디서 살 수 있는가

```sql
CREATE TABLE release_links (
    id         BIGSERIAL PRIMARY KEY,
    release_id BIGINT NOT NULL REFERENCES releases(id) ON DELETE CASCADE,
    source_id  TEXT REFERENCES sources(id),   -- 등록된 소스면 연결, 아니면 NULL
    shop_name  TEXT NOT NULL,                 -- 소스 미등록 판매처도 자유 입력
    url        TEXT NOT NULL,
    price_krw  NUMERIC(12,0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (release_id, url)
);
```

`listings` 를 재활용하지 않는 이유: `source_item_id`·`content_hash` 가 `NOT NULL` 인데
수동 등록에는 존재하지 않는 값이다. 제약을 느슨하게 만들면 크롤 경로의 불변식이 약해진다.

### 5.3 `listing_events.listing_id` 를 NULL 허용으로

수동 등록 일정에서 나온 이벤트는 `listing` 이 없다. `release_id` 를 주 앵커로 쓴다.
`event_type` CHECK 목록에 `SCHEDULE_ADDED`, `PREORDER_OPENS_SOON`, `RELEASED` 를 추가한다.

## 6. 마일스톤 재편

| 새 마일스톤 | 목표 |
|---|---|
| **M0**(완료분 유지) | 스캐폴딩·스키마·수집기 부품 — 이미 완료 |
| **M1** | **수동 등록 → 공개 피드**. 관리 API, `/v1/releases`, `/v1/feed`, RSS, iCalendar, 웹 피드·캘린더 |
| **M2** | **시각 기반 알림**. 스케줄러가 `preorder_opens_at` 을 보고 발송. Web Push(계정 불필요 구독, ADR-0006에서 확정) |
| **M3** | **자동 수집 재개**. 잠들어 있던 어댑터를 배선. 수동 등록과 병존 (`curation` 으로 구분) |
| **M4+** | 계정·워치리스트·iOS·푸시. 경량 병합·검색은 필요해질 때 |

**보류(삭제 아님)**: 기존 T-019~T-022(별칭·병합·가격비교), T-025(pg_trgm 검색).

## 7. 감수하는 것

- **운영자 노동이 든다.** 발매 일정을 사람이 넣는다. 주당 20~30건 규모면 감당 가능하나,
  소스가 늘면 병목이 된다. 그 시점이 M3(자동 수집 재개)의 트리거다
- **커버리지가 운영자에게 달린다.** 놓친 발매는 앱에도 없다.
  자동 수집이 붙기 전까지는 이 위험이 그대로 남는다
- **§1.3 의 "병합 정확도" 지표가 당장 측정 불가**하다. 수동 등록에는 중복이 거의 없다.
  이 지표는 M3 이후로 미룬다

## 8. 성공 지표 재정의

기존 §1.3 을 이 제품 정의에 맞게 바꾼다.

| 지표 | 목표 |
|---|---|
| 등록된 일정 수 (주간) | 20건 이상 |
| 예약 시작 알림 발송 성공률 | ≥ 99% (시각 기반이므로 누락은 버그다) |
| 알림 발송 시각 오차 | ±1분 |
| 일정 등록 → 공개 피드 노출 | 즉시 |
| 파서·발송 무음 실패 | 0건 |

"신규 상품 등록 → 앱 노출 지연 30분"은 자동 수집 지표이므로 M3 로 이동한다.
